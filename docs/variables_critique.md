# Критический аудит переменных конструктора Wolf

## Документ №1: Банковская справка 3 мес. (Т-Банк) (`bank_statement_3m__tbank`)

## 1. Исполнимость правил по переменным

- **doc_no** — ⚠️ правило противоречиво: формат «2 буквы + 8 цифр», но примеры `79455`, `6318`, `0426258` — только цифры. Нужно: «Брать строку после `No ` из справки Т-Банка как есть, без нормализации. Если в справке формат `XX########` — сохранять; если только цифры — сохранять цифры».
- **card_mask** — ✅ исполнимо. Уточнить: «последние 4 цифры номера карты из справки/анкеты; если карт несколько — брать карту, по которой идут операции в выписке».
- **ref_no** — ⚠️ правило смешивает две сущности (референс + дата). Разделить: `ref_no` = `<буква><8 цифр><3 буквы>`; `ref_date` = дата справки = `period_to`.
- **address_live** — ⚠️ правило описывает транслит, но не источник выбора между РФ-форматом и иностранным. Уточнить: «Если страна = RU → формат `<индекс>, <Obl/Krai>, G <город>, Ul <улица>, D. <дом>[, Korp. <корп>], Kv. <кв>`; иначе — адрес как в анкете, латиницей».
- **client_name** — ✅ исполнимо, но нужен явный источник: «загранпаспорт (латиница) → если нет, транслит по правилам».
- **period_from** — ✅ исполнимо (minus_months(3) от balance_date).
- **period_to** — ✅ исполнимо (= statement_date).
- **balance_rub** — ⚠️ правило не указывает источник. Уточнить: «Остаток на счёте на дату `period_to` из выписки Т-Банк; сумма прописью генерируется автоматически».
- **doc_date** — ✅ исполнимо, но дублирует `period_to` (см. п.2).

## 2. Дубли и пропуски

**Дубли (одно значение, разные имена):**
- `period_to` = `doc_date` = `ref_date` (дата справки). Оставить одну переменную `statement_date`, остальные — производные.
- `ref_no` содержит дату, которая уже есть в `period_to` — расщепить.

**Не хватает переменных:**
- `statement_date` — базовая дата, от которой считаются `period_from`, `period_to`, `doc_date`.
- `balance_date` — упоминается в правилах, но не объявлена.
- `bank_name` / `bank_branch` — для шапки справки.
- `account_number` / `iban` — обычно есть в выписке.
- `currency` — жёстко «rubles», но для нерезидентов может быть иная.
- `client_dob`, `passport_no` — часто требуются в визовых пакетах.
- `signatory` / `bank_officer` — подписант справки.
- `statement_language` — RU/EN (влияет на транслит адреса).

## 3. Противоречия и риски автозаполнения

- **doc_no**: формат vs примеры — прямой конфликт, автозаполнение сломается на цифровых номерах.
- **ref_no**: склейка референса и даты → риск двойного пробела/формата; дата может не совпасть с `period_to`, если парсер возьмёт её из письма.
- **address_live**: смешение RU-транслита и иностранного адреса в одном правиле → риск применить транслит к казахстанскому/индонезийскому адресу.
- **balance_rub**: не указан источник → риск подставить годовой/месячный баланс вместо баланса за период.
- **client_name**: регистр (CAPS vs Title Case) в примерах разный — нужен единый стандарт (обычно как в загранпаспорте).
- **period_from**: `minus_months(3)` на 29–31 числах даёт «съезд» (30.11 → 30.08 vs 31.08) — зафиксировать правило end-of-month.
- **card_mask**: при нескольких картах — неоднозначность выбора.

## 4. Что автоматизировать в первую очередь

1. **Даты** (`statement_date` → `period_from`, `period_to`, `doc_date`, `ref_date`) — чистый расчёт, максимальный риск ручной ошибки.
2. **Сумма прописью** (`balance_rub`) — генерация из числа, исключает опечатки.
3. **Транслит ФИО** (`client_name`) — по правилам загранпаспорта, с fallback-словарём.
4. **Транслит адреса** (`address_live`) — конвертер RU→латиница с шаблоном `Obl/G/Ul/D/Kv`.
5. **`card_mask`** — извлечение последних 4 цифр из номера карты в выписке.
6. **`ref_no`** — regex-извлечение из письма-справки (после стабилизации формата).
7. **`doc_no`** — в последнюю очередь: формат нестабилен, нужен ручной контроль или правило «как в источнике».

## Документ №2: Банковская справка 3 мес. (Сбер) (`bank_statement_3m__sber`)

## 1. Правила по переменным

- **doc_no** — неоднозначно. «Номер выписки» и «уникальный ref_no» пересекаются. Уточнить: `doc_no` = внутренний номер документа в системе агентства (генерируется автоматически, формат `YYYYMMDD-NNN`), не путать с банковским.
- **card_mask** — правило противоречиво: «первые 12 скрыты, последние 4 видны» vs примеры `1234 **** **** 5678` (видны первые 4 и последние 4). Зафиксировать: `**** **** **** 1234` (только последние 4).
- **ref_no** — ок, но пример `Ref.\n9922732e` нарушает «верхний регистр». Убрать перенос строки и нижний регистр из примеров.
- **address_live** — не указан обязательный порядок и наличие индекса. Уточнить: `[ИНДЕКС,] СТРАНА, ГОРОД, УЛИЦА, ДОМ[, КВ.]`, всё латиницей, верхний регистр.
- **client_name** — ок. Добавить: строго как в загранпаспорте (MRZ), без отчества, если в паспорте его нет.
- **doc_date** — два формата в одном правиле → риск. Зафиксировать один: `DD.MM.YYYY`.
- **balance_rub** — правило ссылается на «12м», а документ — 3 мес. Исправить: «среднемесячный/совокупный доход за 3 мес.». Формат: `1 234 567.89` (пробел-разделитель, точка-десятичная, без ₽).
- **account_no** — ок, но пример `30101810400000000225` — корсчёт, не лицевой. Убрать.
- **contract_date** — ок, зафиксировать `DD.MM.YYYY`.
- **contract_no** — ок, но нет маски/шаблона. Добавить: только `[A-Z0-9/-]`, до 20 символов.

## 2. Дубли и пропуски

Дубли (одно значение — разные имена):
- `doc_no` ↔ `ref_no` — оба «номер выписки/запроса». Оставить один.
- `contract_no` ↔ `account_no` — если договор = счёт, объединить; иначе явно развести.

Не хватает:
- **bank_name / bank_branch** (Сбер, конкретное отделение) — обязательно для справки.
- **bank_bic / correspondent_account** — для верификации.
- **currency** (RUB явно, но нужен код ISO).
- **period_from / period_to** — период выписки (3 мес.) — критично, сейчас нет.
- **client_passport_no** — для сверки ФИО с загранпаспортом.
- **signature_stamp** (флаг наличия подписи/печати) — влияет на валидность.
- **issue_place** (город выдачи) — часто требуется консульством.

## 3. Противоречия и риски автозаполнения

- `card_mask`: правило ≠ примеры → маска сгенерируется неверно.
- `doc_no` vs `ref_no`: два поля из одного источника → дублирование или рассинхрон.
- `doc_date`: два формата → парсер выберет не тот.
- `balance_rub`: ссылка на «12м» → подтянется неверная сумма.
- `client_name`: примеры в нижнем регистре и с отчеством → нарушение «как в загранпаспорте».
- `address_live`: примеры без индекса и с индексом → нестабильный формат.
- `account_no`: пример корсчёта → подстановка чужого типа счёта.
- `ref_no`: пример с `\n` и нижним регистром → сломает шаблон.

## 4. Что автоматизировать в первую очередь

1. **Даты** (`doc_date`, `contract_date`) — из системных полей, единый формат `DD.MM.YYYY`.
2. **ФИО латиницей** (`client_name`) — транслитерация из загранпаспорта (MRZ), верхний регистр.
3. **Маска карты** (`card_mask`) — из номера карты, шаблон `**** **** **** NNNN`.
4. **Номер счёта** (`account_no`) — валидация 20 цифр + контроль по БИК.
5. **Сумма** (`balance_rub`) — расчёт из выписки за период, формат `1 234 567.89`.
6. **Период выписки** (`period_from/to`) — вычисляется от `doc_date` минус 3 мес.
7. **ref_no / doc_no** — генерация по единому правилу (один источник, один формат).
8. **Адрес** — нормализация из карточки клиента в единый шаблон.

## Документ №3: Резюме (CV) — короткий формат (`cv__format_short`)

## 1. Правила по переменным

**passport_no**
- Правило исполнимо, но неполно: не указано, что делать с пробелами/дефисами и что брать при расхождении с MRZ.
- Уточнить: «Брать строку из поля "номер паспорта" карточки клиента без изменений. Пробелы и дефисы сохранять как в источнике. Если в карточке есть отдельно серия и номер — склеить через пробел. Латиница/цифры — верхний регистр. Не нормализовать, не удалять пробелы.»

**date_of_birth**
- Правило противоречиво: «Month DD, YYYY **или** DD.MM.YYYY» — два взаимоисключающих формата в одном шаблоне. Плюс пример `1987-10-26` не соответствует ни одному из заявленных.
- Уточнить: «Брать из поля "дата рождения" карточки клиента. Приводить к формату `Month DD, YYYY` (например, `October 26, 1987`). Если в источнике ISO (`YYYY-MM-DD`) — конвертировать. Локаль — en-US, месяц — полным английским словом.»

## 2. Дубли и пропуски

**Дубли:** в явном виде нет (обе переменные уникальны).

**Не хватает (по смыслу CV):**
- `full_name_latin` — ФИО латиницей как в паспорте (ключевое для визы).
- `nationality` / `citizenship`.
- `gender` (часто требуется в визовых анкетах).
- `passport_issue_date`, `passport_expiry_date`, `passport_issuer`.
- `place_of_birth`.
- `contact` (телефон/email) — для CV.
- `photo` — если шаблон подразумевает.
- `address` (текущий адрес).

## 3. Противоречия и риски автозаполнения

- **Формат даты:** «или/или» + третий пример → шаблонизатор не знает, какой формат рендерить. Риск: разные документы в одном пакете с разными форматами.
- **passport_no:** примеры `123456789`, `75 1234567`, `AB1234567` показывают, что длина и структура разные. Без правила нормализации возможны потери пробела или лишние символы → несоответствие MRZ.
- **Отсутствие ФИО латиницей** — критично: в CV для визы имя должно совпадать с паспортом, а не с кириллицей из карточки.
- **Нет правила fallback:** что делать, если поле пустое в карточке (оставить пустым / взять из MRZ / блокировать генерацию).

## 4. Что автоматизировать в первую очередь

1. **ФИО латиницей** — из MRZ паспорта или транслитерацией по ICAO Doc 9303 (не «на глаз»).
2. **Дата рождения** — единый формат `Month DD, YYYY`, конвертация из ISO/DD.MM.YYYY.
3. **Номер паспорта** — брать как есть из MRZ-строки (там эталон), а не из ручного поля карточки.
4. **Даты паспорта** (issue/expiry) — вычислять/тянуть из MRZ, проверять срок действия ≥ 6 мес. от даты поездки.
5. **Nationality / gender** — из MRZ (позиции 2–3 и 21).
6. **Возраст** — вычислять из даты рождения, если нужен в CV.

## Документ №4: Резюме (CV) — расширенный формат (`cv__format_detailed`)

## 1. Оценка правил переменных

**client_photo_url**
- Правило исполнимое, но неполное: не указано, что делать, если фото нет / не загружено / битый файл.
- Уточнить: «Если `get_client_photo_data_uri()` возвращает пусто или ошибку — подставлять плейсхолдер `[PHOTO]` и логировать warning. Формат: `data:image/jpeg;base64,...`. Не хранить URL — только data URI.»

**passport_number**
- Правило понятное, но «точно как в паспорте» конфликтует с примерами: `123456789` (9 цифр) и `75 1234567` (2+7) — это разные форматы, значит источник неоднородный.
- Уточнить: «Брать из `client.passport_number` без нормализации. Если поле пустое — блокировать генерацию. Пробелы/серию сохранять как в источнике; не тримить внутренние пробелы, только края.»

## 2. Дубли и пропуски

**Дубли (потенциальные):**
- `client_photo_url` vs возможный `client_photo_base64` — если где-то ещё есть фото, будет рассинхрон.
- `passport_number` vs `passport_series` / `passport_no` — если в других документах они разделены, здесь склеены → риск разного формата в разных шаблонах.

**Не хватает (по смыслу CV):**
- `full_name_latin` (ФИО латиницей как в загранпаспорте) — ключевое для визы.
- `date_of_birth`, `place_of_birth`, `nationality`, `gender`.
- `passport_issue_date`, `passport_expiry_date`, `passport_issuer`.
- `address`, `phone`, `email`.
- `education[]`, `work_experience[]` (структурированные: компания, должность, период, описание).
- `marital_status`, `children`.
- `date_of_cv` / `signature` (для расширенного формата).
- `photo_spec` (требования к фото: 3x4, белый фон) — если шаблон верстает фото.

## 3. Противоречия и риски автозаполнения

- **Формат паспорта**: примеры несовместимы → парсер может «нормализовать» и испортить серию.
- **Фото**: base64 в шаблоне → раздувание документа, риск превышения лимитов; нет fallback.
- **Отсутствие ФИО латиницей**: если берётся из кириллицы транслитом — расхождение с загранпаспортом → отказ визы.
- **Нет валидации дат** (issue/expiry) — легко подставить просроченный паспорт.
- **Нет проверки обязательных полей** — CV уйдёт с пустыми блоками.

## 4. Что автоматизировать в первую очередь

1. **ФИО латиницей** — из загранпаспорта (MRZ), не транслит.
2. **Даты** (рождения, выдачи, окончания паспорта) — из MRZ/карточки, с валидацией «не просрочен».
3. **Возраст / стаж** — вычисляемые из дат.
4. **Периоды работы/учёбы** — автоформат `MM.YYYY – MM.YYYY`, автосортировка по убыванию.
5. **Фото** — авто-ресайз до 3x4, JPEG, fallback-плейсхолдер.
6. **Номер паспорта** — брать как есть, без нормализации; валидировать только длину/наличие.
7. **Контакты** — из карточки клиента, формат телефона в E.164.

## Документ №5: Резюме (CV) — формат Сиваева (`cv__format_CLIENT`)

## 1. Оценка правил по переменным

**company**
- Правило «Источник уточняется» — неисполнимо. Непонятно, откуда брать значение.
- Предложение: «Из карточки клиента поле "Текущий работодатель". Если пусто — уточнить у клиента; в CV писать полное юридическое название на латинице (как в трудовом договоре/справке).»

**date_of_birth**
- Правило понятное, но допускает 3 формата — риск неконсистентности в одном документе.
- Предложение: «Из карточки клиента поле "Дата рождения". Приводить к единому формату: `Month DD, YYYY` (например, `October 26, 1987`). Если в карточке иной формат — конвертировать.»

**passport**
- Правило понятное, но «точно как в паспорте» конфликтует с примерами (`123456789`, `75 1234567`, `AB1234567`) — это разные типы документов.
- Предложение: «Из карточки клиента поле "Номер паспорта". Копировать без изменений, включая серию и пробелы. Если в карточке нет пробела, а в паспорте есть — привести к виду паспорта.»

## 2. Дубли и недостающие переменные

**Дубли:** не обнаружены (переменные разного смысла).

**Не хватает (по смыслу CV):**
- `full_name_latin` — ФИО латиницей (как в загранпаспорте)
- `nationality` — гражданство
- `place_of_birth` — место рождения
- `passport_issue_date` / `passport_expiry_date` — срок действия
- `address` — адрес проживания
- `phone`, `email` — контакты
- `education` — образование (вуз, годы, специальность)
- `work_experience` — опыт работы (компания, должность, период, обязанности)
- `position` — текущая должность
- `photo` — фото (если требуется форматом)
- `signature_date` / `place` — дата и место подписания

## 3. Противоречия и риски автозаполнения

- `date_of_birth`: три допустимых формата → в одном документе может оказаться смесь. Нужен один формат.
- `passport`: «точно как в паспорте» vs примеры с разной структурой → OCR/парсер может нормализовать и испортить (убрать пробел, серию).
- `company`: нет источника → автозаполнение невозможно, поле уйдёт пустым или с мусором.
- Отсутствие `full_name_latin` при наличии `passport` — риск, что имя в CV не совпадёт с паспортом (частая причина отказа).
- Нет валидации: дата рождения в будущем, паспорт с истёкшим сроком, несоответствие ФИО и паспорта.

## 4. Что автоматизировать в первую очередь

1. **`full_name_latin`** — из загранпаспорта (MRZ) или транслитерация по стандарту ICAO из кириллицы.
2. **`date_of_birth`** — парсинг любого входного формата → единый `Month DD, YYYY`.
3. **`passport`** — извлечение из MRZ/скана, сохранение серии и пробелов как в оригинале.
4. **`passport_issue_date` / `passport_expiry_date`** — из MRZ (позиции 14–19 и 20–25).
5. **`company`** — подтягивать из карточки клиента; при отсутствии — блокировать генерацию и запрашивать.
6. **Валидации:** срок паспорта ≥ 6 мес. от даты поездки; дата рождения < сегодня; ФИО латиницей = MRZ.

## Документ №6: D12: Permohonan Visa (ходатайство) (`d12_cover_letter__default`)

## 1. Исполнимость правил по переменным

- **client_name** — исполнимо, но неполно: не указан порядок транслитерации (surname-first или name-first), стандарт (ICAO/ГОСТ/BSI), регистр. Уточнить: «ФИО латиницей в порядке Surname Given Patronymic, uppercase, стандарт ICAO Doc 9303; источник — clients.full_name_latin, fallback — транслитерация по ICAO».

- **client_name** — понятно, но «ь опускается, -а→-a» не покрывает `ё→e` в середине (пример: Grigoreva). Уточнить: *«Транслит по загранпаспорту; если паспорта нет — по таблице я→ya, ё→e, ь→(пусто), й→y, -ая→-aya.»*
- **contract_no** — понятно (10 цифр).
- **account_no** — понятно (20 цифр), но источник «справка на Drive» — не привязан к полю. Уточнить: *«`clients.account_no`; fallback — 20-значный счёт из шапки выписки Т-Банк.»*
- **balance_rub** — понятно, но «остаток на дату письма» vs «баланс за период» — противоречие внутри правила. Уточнить: *«Остаток на конец периода `As from … to <doc_date>`; формат `<N NNN, KK> rubles (<прописью> rubles KK kopeks)`.»*
- **doc_date** — понятно, но дублирует конец периода и ref_no-дату. Уточнить: *«= дата окончания периода движения средств; единственный источник — шапка выписки.»*
- **contract_date** — понятно.

## 2. Дубли и пропуски

**Дубли (одно значение — разные имена):**
- `doc_date` = дата в `ref_no` = конец периода в шапке выписки.
- `doc_no` vs `contract_no` — оба «номер», но разные сущности; риск путаницы при OCR.
- `account_no` vs `contract_no` — оба 20/10 цифр, легко перепутать при автозаполнении.

**Не хватает переменных:**
- `period_start` — начало периода «As from … to …» (нужно для валидации 12 мес.).
- `period_end` — явно, а не через doc_date.
- `bank_name` / `bank_branch` — шапка справки.
- `currency` — если счёт не только RUB.
- `signatory` — ФИО/должность подписанта банка.
- `client_dob`, `client_passport` — для сверки ФИО латиницей.
- `statement_language` — RU/EN (влияет на транслит адреса).
- `total_turnover` — если требуется по требованиям визы (часто нужен оборот за 12 мес., а не только баланс).

## 3. Противоречия и риски автозаполнения

- **ref_no**: пример без даты vs правило «+ дата» — риск рассинхрона с `doc_date`.
- **balance_rub**: «на дату письма» vs «за период» — при парсинге можно взять не тот остаток (начальный/конечный/средний).
- **doc_no**: два источника без приоритета → расхождение номера в шапке и в карточке.
- **address_live**: транслит без стандарта → разные варианты одного адреса, отклонение визовым офицером.
- **client_name**: регистр (пример `POZNYAK CLIENT DMITRIEVNA` vs `CLIENT_011 Aleksandrovna`) — нет правила регистра.
- **card_mask**: при нескольких картах — неясно, какую подставлять в описание операций.
- **doc_date = contract_date?** — если договор открыт в том же месяце, легко перепутать при OCR.
- **account_no (20 цифр) vs contract_no (10 цифр)** — при потере разделителей OCR может «склеить»/«разрезать».

## 4. Что автоматизировать в первую очередь

1. **Даты-производные**: `doc_date` = `period_end` = дата в `ref_no`; `period_start` = `period_end − 12 мес.` Валидация: `contract_date ≤ period_start`.
2. **ФИО латиницей** (`client_name`) — из загранпаспорта/анкеты через единый транслит-модуль (ГОСТ Р 7.0.34 / ICAO). Один источник — один результат.
3. **Адрес** (`address_live`) — шаблонизатор из структурированных полей анкеты (индекс, регион, город, улица, дом, корп., кв.) + транслит.
4. **Сумма прописью** (`balance_rub`) — генератор «цифры + прописью + kopeks» из числа.
5. **Номера** (`account_no`, `contract_no`, `doc_no`) — regex-валидаторы (20/10 цифр, буквенно-цифровой) + fallback-источник с приоритетом.
6. **`card_mask`** — извлекать из строк операций выписки (последние 4 цифры в описании), а не из карточки.
7. **`ref_no`** — собирать как `ref + " " + doc_date` из одного источника, чтобы не расходилось.

## Документ №24: Банковская справка 12 мес. (Сбер) (`bank_statement_12m__sber`)

## 1. Оценка правил по переменным

- **doc_no** — ⚠️ неоднозначно. «Номер выписки» vs примеры `No 12345`, `2025/04/123`, `ae32271197` — формат не числовой. Правило: «Номер выписки из банковской системы, как отображается в оригинале, до 20 символов, буквы/цифры/`/`/`-`».
- **card_mask** — ⚠️ противоречие. Правило: «первые 12 скрыты, последние 4 видны», но примеры `1234 **** **** 5678` и `1234 56** **** 7890` показывают первые 4–6 цифр. Уточнить: «первые 6 и последние 4 видны, середина — `*`» (стандарт PCI) ИЛИ «первые 4 и последние 4». Привести примеры к одному виду.
- **ref_no** — ✅ понятно. Добавить: «если в выписке нет — генерировать `SBR-YYYY-NNNNNN`».
- **address_live** — ⚠️ нет правила транслитерации и порядка. Уточнить: «латиница, порядок: CITY, STREET, HOUSE, APT; индекс опционально; без запятых внутри полей».
- **client_name** — ⚠️ конфликт примеров (кириллица + разный регистр). Правило: «латиница строго как в загранпаспорте, UPPERCASE, порядок SURNAME GIVEN NAME PATRONYMIC».
- **doc_date** — ⚠️ три формата в примерах. Зафиксировать один: `DD.MM.YYYY`.
- **contract_date** — ⚠️ то же: зафиксировать `DD.MM.YYYY`.
- **contract_no** — ✅ понятно, но добавить «как в договоре, без нормализации».
- **account_no** — ⚠️ примеры с пробелами и 20 цифр. Правило: «20 цифр без пробелов».
- **balance_rub** — ⚠️ «доступный доход за период» — не то же, что «баланс». Уточнить: «сумма поступлений за 12 мес. (кредитовые обороты) минус внутренние переводы; формат `1 234 567.89` (пробел-разделитель, точка-десятичная)».

## 2. Дубли и пропуски

**Дубли (по смыслу):**
- `doc_no` ↔ `ref_no` — оба «номер выписки/запроса». Развести: `doc_no` — номер выписки банка, `ref_no` — номер заявки агентства.
- `contract_date` ↔ `doc_date` — не дубли, но часто совпадают при генерации; проверить логику.

**Не хватает:**
- `bank_name` / `bank_branch` — Сбер, конкретное отделение (для шапки).
- `bic` / `corr_account` — реквизиты банка.
- `client_dob` — дата рождения (часто требуется в выписке).
- `passport_no` — номер загранпаспорта (сверка ФИО).
- `currency` — валюта счёта (RUB по умолчанию, но явно).
- `period_from` / `period_to` — период выписки (12 мес.).
- `signature_official` / `stamp` — подпись/печать (флаг наличия).
- `issue_city` — город выдачи.

## 3. Противоречия и риски автозаполнения

- **card_mask**: правило vs примеры — прямое противоречие → риск утечки/некорректной маскировки.
- **client_name**: кириллица в примерах при правиле «латиница» → риск подстановки кириллицы.
- **doc_date / contract_date**: 3 формата → риск несоответствия шаблону.
- **balance_rub**: «доход» vs «баланс» — семантическая ошибка, критично для визового офицера.
- **doc_no**: пример `ae32271197` (нижний регистр) при правиле «числовой» → падение валидатора.
- **account_no**: пробелы в примерах при правиле «20 цифр» → риск несовпадения с банковской выпиской.
- **address_live**: отсутствие правила транслитерации → разные агенты введут по-разному.

## 4. Что автоматизировать в первую очередь

1. **client_name** — транслитерация из кириллицы по стандарту загранпаспорта (ICAO Doc 9303), UPPERCASE.
2. **address_live** — транслитерация + нормализация формата.
3. **doc_date / contract_date** — единый формат `DD.MM.YYYY` из ISO-даты источника.
4. **balance_rub** — расчёт из выписки (сумма кредитовых оборотов), формат с пробелами.
5. **account_no / card_mask** — нормализация (убрать пробелы / применить маску по единому правилу).
6. **ref_no** — генерация по шаблону `SBR-YYYY-NNNNNN`, если нет в источнике.
7. **doc_no** — извлечение из PDF выписки регуляркой, fallback — генерация.
