# Wolf AutoDoc — вводная для новой сессии

Документ для начала работы «с чистого листа»: как система думает, а не какие
баги починены. Читать перед тем, как что-то менять.

## 1. Смысл системы

Wolf AutoDoc собирает для клиента **пакет документов под конкретный визовый
продукт** и «Легенду» — связный рассказ о клиенте, который печатается вместе с
пакетом и даётся клиенту на руки: что за документы у него на руках и что он
должен уметь рассказать.

Правильный вопрос при любой правке: **не «какая переменная не подставилась», а
«какую историю о клиенте рассказывает этот документ и не спорит ли она с
остальными»**.

## 2. Поток данных (по нему проверять любую правку)

```
продукт (C1-EXT, E33G-NEW, BRIDGING, CONV, D12)
   │  requirements.py  — что этот регламент ТРЕБУЕТ
   ▼
пакет документов            package.py  — какие документы подаём (один на слот)
   │
   ▼
значения для бланка         CLIENT.py + addresses.py  — что печатаем в каждом
   │
   ▼
документ                    render.py → PDF
   │
   ▼
проверки                    doc_check, pdf_CLIENT, final_check, reader_CLIENT
                            (документы ВМЕСТЕ с легендой)
```

Значение ищут от источника к документу. Если источник один, а правила два — они
спорят, и печатается то, что успело записаться последним (так было с адресом:
пять блоков в `CLIENT.py` перебивали друг друга).

## 3. Принципы, которые нельзя нарушать

1. **Легенда строится от требований продукта, а не от данных клиента.**
   Если регламент не спрашивает работу и доход — их в легенде нет, и система не
   требует их у клиента.
2. **Набор документов задаёт продукт, а не клиент.** У одного продукта справка
   Т-Банка, у другого — Сбера; в слоте всегда один документ.
   Так же с договором: он **один на клиента**, выбор по продукту —
   E33G-NEW, E33G-EXT, D12 → Remote Work Agreement (подтверждает удалённую работу
   и годовой доход), C1, C1-EXT, BRIDGING, CONV → Employment Contract.
   Правило проверено по архиву Диска (85 папок, 145 заявок): E33G и D12 всегда
   получали Remote Work Agreement, визитные — трудовой договор.
   Форма E-02 — **свой слот** (`e02`), она не альтернатива письму в иммиграцию:
   в комплекте Bridging обе лежат одновременно.
3. **Два адреса клиента — разные поля.**
   `address_live` — адрес в стране гражданства (Россия): банковские справки,
   договоры, резюме. `address_in_indonesia` — адрес пребывания: письма в
   иммиграцию, заявления, формы E-02. Банк РФ не может выдать справку человеку с
   балийским адресом.
   Единственный арбитр — `CLIENT/addresses.py`, деление адреса на две строки
   тоже только там.
4. **Работа — вне Индонезии.** Клиент работает в российской (или любой
   неиндонезийской) компании. Индонезийская фирма в пакете допустима как
   спонсор визы, но не как работодатель.
5. **Финансовые цифры.** Даёт ли клиент реальную справку и проходит ли она порог
   регламента: проходит — берём её сумму; не проходит или справки нет — система
   готовит документ с проходной суммой, и клиент рассказывает именно её.
6. **Лишний документ выключается, а не «отклоняется».** Статус `excluded`:
   проверки его не видят, в легенде он в разделе «не подаётся» с причиной.
7. **Проверка — только вместе.** Состав пакета + легенда + регламенты +
   визуальный контроль. Вердикт разделяет: `autofix` (наша ошибка),
   `client_data` (нужны данные клиента), `template` (переделать бланк).
8. **Остановка конвейера — это событие.** Каждый стоп фиксируется с причиной;
   молча пропускать нельзя.

## 4. Как работать с системой

```bash
# весь конвейер по заявке (без отправки клиенту)
PYTHONPATH=/opt/wolf_v2 /usr/bin/python3 scripts/auto_cycle.py 111 --no-send

# что попало в документ на самом деле
PYTHONPATH=/opt/wolf_v2 /usr/bin/python3 CLIENT/pdf_CLIENT.py 111

# легенда клиента так, как её прочитает клиент
PYTHONPATH=/opt/wolf_v2 /usr/bin/python3 -c "
from CLIENT import legend as lg
print(lg.render(lg.build(92, app_id=111, CLIENT_code='C1-EXT')))"

# оба адреса и какой берёт каждый документ
PYTHONPATH=/opt/wolf_v2 /usr/bin/python3 -c "
from CLIENT import addresses as A
print(A.client_addresses({'id':92}, 92))"
```

Интерпретатор — `/usr/bin/python3` (у него есть зависимости проекта).
База — `data/wolf.db`, бэкапы — `data/backup/`.

## 5. Известные ловушки

- **Адрес делится в двух местах** → строки накладываются. Делить только в
  `addresses.split_two_lines`.
- **`en_order` должен быть идемпотентным**: повторный проход по уже
  переставленному адресу теряет дом и квартиру.
- **`available balance` стоит в заголовке справки** перед адресом банка — поиск
  суммы по первому вхождению даёт неверное число.
- **Файлы с Диска приходят без расширения** — переименовывать, не копировать
  (копия выглядит в заявке как задвоение документов).
- **`db.py`**: `exec_sql()`; `q1()` — одна строка, `q()` — список.
- **Схема ≠ код**: полей `CLIENT.price_idr`, `CLIENT.CLIENT_name` нет.
