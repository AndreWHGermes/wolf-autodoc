# Аудит: почему документы не выдаются быстро и безошибочно

Дата: 06.10.2026. Объект: Wolf AutoDoc v2 (/opt/wolf_v2) — конструктор визовых документов.
Основание: разбор кода и базы, замеры по факту, сравнение с промышленными подходами (PDF overlay / AcroForm / HTML→PDF / DOCX-шаблоны).

---

| Показатель | Значение |

Технически документ собирается так: настоящий PDF-образец → разбор на HTML с **абсолютными координатами** (контракт №18 — 165 блоков, справка — 67 блоков) → подстановка значений (`render.fill`) → печать WeasyPrint в PDF.

## 2. Вопрос 1. Самые стабильные пути решения

По устойчивости (от самого надёжного для «идентичного внешнего вида»):

**A. Overlay поверх оригинального PDF («штамп по подложке»)** — самый стабильный.
Оригинальный бланк остаётся байт-в-байт, значения печатаются поверх: `PyMuPDF insert_textbox` в рамку исходного значения, либо anchor-подход — найти текст-метку (`page.search_for("Date of CLIENT")`) и печатать справа от неё на той же базовой линии. Плюсы: невозможно «сломать вёрстку» (её не пересобирают), нет потери блоков, нет наложений, оригинальные логотипы/печати/QR остаются; устойчиво к мелким сдвигам бланка. Минус: длинный многострочный текст (обязанности, приложения) нужно печатать в рамку с автопереносом, а «затирать» старое значение — белым прямоугольником (делать только поверх пустых полей либо на белом фоне).

**B. HTML→PDF (то, что у нас)** — рабочий, но самый хрупкий из трёх.
Стабилен только если HTML точно повторяет бланк. Любая правка бланка = переразбор 165 блоков, отсюда наложения, потерянные строки, обрезка, «вылезает за край». Оправдан там, где макет сложный и меняется содержательно (резюме, договор с переменным числом пунктов).

**C. AcroForm / XFA** — только для интерактивных бланков. Наши клиентские PDF плоские (flat), полей нет — путь не применяется.

**D. DOCX-шаблоны (docxtpl) → PDF** — годится, если бланк изначально Word и требуемая точность «как Word», а не «как PDF листа». Конвертация DOCX→PDF на Linux стабильностью не блещет (это известная проблема), для юридических форм рискованно.

Итог: **массовые одностраничные формы (справки банка, письма, E-02, D12) выгодно перевести на путь A**; конструктор HTML оставить для многостраничных сложных (договоры, резюме) — или тоже переводить на A по мере стабилизации.

## 3. Вопрос 2. Что мы делаем правильно и что нет

**Правильно**
- Храним **настоящий эталон** и фиксируем хэш (`data/originals/` + MANIFEST) — защита от подмены бланка.
- Сборка **детерминированная**: шаблон + значения; LLM не участвует в числах/датах.
- **Единый источник данных на заявку** (организация одна в резюме, договоре №11, контракте №18 — `org_pool` + `_org_for_CLIENT`).
- Каталог переменных с описанием правила (446 из 450) — база для автозаполнения.
- Авто-проверки и сверка «наш документ ↔ образец» (детектор вёрстки, side-by-side PNG) — правильный инструмент контроля.
- Один каркас на вариант (письма, офисы через переменные) — верное направление.

**Неправильно**
1. **Мы пересобираем бланк в HTML.** Это и есть корень нестабильности: 165 блоков с координатами в pt на один договор, ручные сдвиги, потерянные при разборе строки, обрезка, 907 бэкапов как следствие.
2. **Латание вместо архитектуры.** 159 скриптов, 3 057 строк эвристик в `CLIENT.py`, десятки «если шаблон такой-то» — правила размазаны по коду, а не описаны данными.
3. **Нет контракта данных.** Приоритеты «карточка → комментарий → документ → пул» заданы кодом; нет схемы «какие поля обязательны для этого документа и чем проверяются».
4. **Нет гейта готовности.** Документ можно собрать с пустым/неверным полем — в PDF уходит либо пустота, либо неверное значение; ошибка ловится глазами оператора.
5. **Правила переменных не утверждены.** 61 из 450 — остальное «как получится»; отсюда «другой текст в конструкторе» и споры о смысле полей.
6. **Нет регрессионных тестов.** Каждая правка проверяется вручную (сборка → PNG → глаза), поэтому правка одного документа ломает другой и никто этого не видит сразу.
7. **Автоперевод документов целиком.** Русский текст длиннее — вёрстка едет (частично лечим `fit_width`), а главное — переводится не то, что нужно: смысл документа рождается из данных, а не из перевода бланка.
8. **Дубли шаблонов** (5 писем из трёх офисов, два класса договоров, merged/hidden) — источник расхождений при правках.

## 4. Вопрос 3. Конкретные ошибки конструктора

1. **Абсолютные координаты как единственный способ вёрстки.** Нет автопереноса по умолчанию: блок с `white-space:pre` CLIENTит за лист (было 16 блоков в 5 шаблонах; `fit_width` это закрыл постфактум, но конструкция остаётся хрупкой).
2. **Разбор PDF даёт дубликаты и потери**: два блока на одной высоте (наложение), склеенные строки, потерянные разделительные линии, кегли 7.65/7.92 вместо 8/8.5.
3. **Значения-подсказки в полях.** Пример: `CLIENT` = «ФАМИЛИЯ@ALPHA-PRIME.GROUP (формула…)» печаталось в документ; `CLIENT_from` содержал целую фразу. Мусор из значений попадает в PDF.
4. **Подмена/несоответствие эталонов.** Для 12m-справок эталоном стояла 126-страничная выписка движений; для Сбера — справка с периодом 15 месяцев (в архиве опечатка). Неверный эталон → неверный шаблон.
5. **Мусор в справочниках.** В пул организаций попали банковские ATM-транзакции, обрывки фраз, дубликаты (325 → почищено до 301); часть организаций без реквизитов использовалась бы в документах.
6. **Незаполненные метки в документе.** `{{company_CLIENT}}` в шаблоне без переменной в базе — метка не подставлялась никогда.
7. **Перевод как изменение HTML.** Перевод меняет длину строк, и без постобработки вёрстка едет; плюс переводится текст бланка, который в документах иммиграции часто должен оставаться на английском.
8. **Нет проверки после сборки.** Собранный PDF никто автоматически не сверяет с эталоном по тексту/координатам — «вылезло/обрезалось» находит человек.

## 5. Вопрос 4. На чём сосредоточиться

**Убрать / остановить**
- Прекратить ручные сдвиги блоков и «доводку глазами» как основной метод.
- Не плодить шаблоны-копии (письма/офисы/классы) — только каркас + переменные варианта.
- Не переводить документ целиком «на лету»; перевод — отдельный слой и только там, где нужен.
- Вынести из проекта 907 бэкапов и разовые скрипты в архив (оставить рабочую папку чистой).

**Добавить (по приоритету)**
1. **Гейт готовности заявки + валидаторы** (1–2 дня): обязательные поля на документ, проверка ИНН/ОГРН контрольной суммой, даты в допустимом окне, суммы в допустимом коридоре, совпадение ФИО/паспорта между документами. Документ не собирается, пока не выполнено.
2. **Golden-регрессия** (1 день): 5–10 реальных заявок → сборка всех документов → автопроверка (нет меток, нет CLIENTа за печатное поле, число страниц, тексты совпадают с эталоном по координатам). Запуск после каждой правки — тогда правки перестают быть рискованными.
3. **Overlay-рендер для массовых одностраничных форм** (3–5 дней): справки, письма, E-02, D12 — печать значений поверх оригинального PDF, оригинал как подложка. Это убирает сам класс ошибок «вёрстка поехала».
4. **Контракт данных** (2–3 дня): JSON-схема на каждый документ (поля, источник, обязательность, валидатор, правило) вместо эвристик в коде; `CLIENT.py` сокращается до сборщика по схеме.
5. **Утвердить правила переменных** (регулярно, по 10–20 за сессию): 61 → 450; без утверждённых правил автоматизация всегда будет «угадывать».

**Итоговый вывод.** Мы правильно делаем данные (единый источник, детерминизм, эталоны) и неправильно — вёрстку: пересобираем бланк вместо того, чтобы печатать значения поверх него. Отсюда 100% текущих ошибок «вылезло за край», «наложилось», «потерялся блок». Быстрый и стабильный результат даст связка: **overlay-рендер поверх эталонного PDF + гейт готовности данных + golden-регрессия**. HTML-конструктор при этом не выбрасывается — он остаётся инструментом для сложных многостраничных документов, но перестаёт быть единственным путём.
